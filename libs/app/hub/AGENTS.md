# SysApps Hub instructions

- Hub has a headless `--hub-sync` entrypoint, independent of c_menu and the interactive session lock. Startup, timer and manual sync must use the same nonblocking host-level sync lock.
- Central provider discovery scans app_*/hub_provider.py (subject to PluginRegistry policy) and trusted `libs/app/hub/sys_hub_plg/*.py`. Collectors expose stable `HUB_PROVIDER_KEY` + `hub_collect(context)`, optionally `hub_apply_remote(updates)`; do not import menu.py for headless collection.
- `HUB_SYNC_MODE` is local only: empty uses legacy HUB_AUTO_SYNC, explicit startup/timer/off overrides it. Never export this knob via SYSAPP1E or silently activate systemd via central settings import.
- Only trusted fixed-schema SQL migrations and writers owned by Hub can modify its database. Collector-local SQL credentials or direct SQL execution are forbidden. Plugin migrations remain future work and require checksummed, namespaced, controlled management.
- Timer unit files must be owned/marked by SysApps, installed atomically, and never overwrite another admin's systemd unit. Mode is persisted only after successful systemd operations.
- In hourly mode, the systemd diagnostic action reads unit properties first (timer enabled/active, LastTriggerUSec, next scheduled run, service Result/ExecMainStatus and completion time), checks current managed unit definitions and reports missing/overdue history. A manual service invocation must require user confirm and must not alter timer state. One-shot exit code 2 from Hub warnings is a failure, not success.
- In hourly mode only, the Hub menu subtitle includes the last service execution (start timestamp and result), using a single read-only systemctl show. This is not the last timer trigger: a manually started service can be the most recent run. Missing/unavailable systemd must not break menu rendering.

- SysApps Hub is a central inventory. MySQL/MariaDB is the transport and storage layer, not the provider API.
- Provider modules never receive a database connection, cursor, table name, SQL fragment, credentials, or migration access. They return typed snapshots only.
- Dynamic `app_*` providers register through module-level `_HUB_PROVIDER_KEY_` and `hub_collect(context)`. Provider keys must be stable, unique, lowercase identifiers.
- A bidirectional provider may additionally expose `hub_apply_remote(updates)`. The central writer returns typed updates only after its transaction commits; a provider must never read the database directly.
- The central runtime maps a fixed dataset name to a fixed writer. A provider cannot select or construct a table name.
- From SysApps 2.4.0, fixed dataset `service` supports a single HubService per drop-in collector (`HubProviderSnapshot(source_key, "service", items)` with zero or one item, stable `service_key=source_key`). Reserve core keys ssh/webmin/ispconfig; the writer only changes its own service key and the core writer must delete only those three core rows, never other providers. This reuses schema 004, no plugin SQL is executed.
- Service collectors report observed state only. Do not import Bacula passwords, SSH private keys, firewall policies, or arbitrary service config; absence of a service and unknown status are distinct. For multiple endpoints or desired-state policy use separately versioned typed schema in a future phase.
- SysApps 2.6.0 includes built-in read-only `app_40_firewall/hub_provider.py` emitting `ufw` service status, with policy parsing and dry-run inside the firewall app. It is not an authorization to modify UFW: no reload, file writes, or automatic Apply on hourly Hub runs. Expiring bans and effective-rule hash handling must remain independent of generated timestamp comments; preserve BOF ownership and order.
- Table identifiers are built only from a strictly validated global prefix and a hard-coded suffix allowlist. All values use parameterized SQL.
- Schema changes belong in ordered `migrations/NNN_name.sql` files. The only supported template placeholder is `{{PREFIX}}`; statements are separated by a line containing exactly `-- statement`.
- Applied migrations are recorded with version and SHA-256. A checksum mismatch is an error and must never be silently accepted.
- Schema UI/safety logic must compare structured current/latest versions from Hub status; never hard-code a historical cutoff such as "schema < 6". Any pending migration on an existing shared DB requires the explicit fleet-updated + database-backup confirmation, while additive pending migrations may still leave Hub READY.
- Each provider synchronizes in its own transaction. A provider failure records an error state and preserves its previous inventory; it must not roll back core host data or other providers.
- Stale provider records may be deleted only after a complete successful snapshot from that provider.
- Hub unavailability, missing schema, missing local service host/FQDN, or provider failure must never block ordinary local sys_apps functions or a successful local Save. Sync requires a normalized service host so inventory never publishes empty or placeholder service URLs.
- Full Hub synchronization must log INFO-level start/done milestones with elapsed time around database readiness, core collection, core DB sync, each provider collection/DB sync/remote apply, and final status refresh. Automatic startup synchronization must additionally expose coarse terminal progress `x/y` over core inventory, each registered provider and finalization; the total is dynamic and this UI progress must not alter provider isolation or provider APIs. Startup centralized-settings download/decode/policy/apply uses the same milestone principle. These logs are operational diagnostics for rare startup stalls and must never include credentials, URL paths containing possible tokens, package contents, or unredacted secrets.
- A terminal that still shows a previous startup line is not proof that Hub synchronization is blocked; correlate it with the runtime milestone log and the `c_menu` RUN/input-wait log before changing Hub synchronization behavior.
- Database passwords must not appear in repr output, logs, error messages, status text, mail, tests, or commits. Exported settings use the versioned password-encrypted one-line package; never add a fixed application encryption key.
- The host identity is the existing `cfg.machineInfo.machine_id`, with `/etc/machine-id` only as a fallback. Do not invent another host ID. The local service host/FQDN/IP is a separate `hosts.service_host` attribute and must never replace or overwrite the system `hostname`/`fqdn`.
- `hosts.name`/`hosts.description` are centrally USER-OWNED and must NEVER be included in host snapshots or UPDATE lists. A NULL `name` means displaying FQDN/hostname dynamically. On-host `auto_sync_enabled` is the real systemd timer unit enablement (NULL unknown), never legacy `HUB_AUTO_SYNC`; it does not prove successful timer execution.
- Schema 005 adds centrally USER-OWNED `host_groups` and single `hosts.group_id INT UNSIGNED NULL` with FK ON DELETE SET NULL. Never collect, auto-assign, reset, or modify group_id or group catalog from host sync. A host with no group remains NULL. Group targeting and source IP aliases are different model domains.
- Schema 006 adds `firewall_rules`; 007 adds independent source/destination port expressions; 008 adds `firewall_vpn_servers` and optional `firewall_rules.vpn_server_uid`. Local firewall collectors own *only* `origin=host_local,target_kind=host` rows for their own machine ID and may replace/delete only that scope. They must never modify `central` or target `group/all` rows. The VPN server UID is scoped by host/target, not globally unique, because deterministic v1 migration may produce the same logical server UID on multiple hosts.
- Firewall config v2 providers require schema >=008 and runtime skips them on older schema without blocking core/other datasets. The compatibility list may include only known additive migrations 005-008; unknown future versions remain blocking. Before applying any shared-DB migration, update every Hub-enabled client to a version that knows it and take a verified DB backup.
- UFW desired-state/policy/SSH remote application remains disabled and unimplemented while schema 005 is staged. Respect the two separately managed and ordered legacy OpenVPN-BAN and Hard Source Allow blocks in before.rules; see docs/firewall-manager-design.md.
- Schema migration 004 is additive but shared-DB rollout MUST be coordinated: older SysApps 2.3.3 requires exact schema 003 and will reject the upgraded schema with `SCHEMA OUTDATED`. Do not apply DB migration or merge for production before planning safe fleet upgrade.
- When the Hub section is present in the last successful central settings signature, its local editor is managed and normally hidden. `--local-settings` is the one-process escape hatch; edits made through it invalidate only `SETTINGS_LAST_APPLIED` so the same central revision is reapplied when the endpoint becomes healthy again. Operational test/schema/sync paths are not central configuration fields.
- Node-RED inventory contains editor/Admin API users and RW/R access only. Never export bcrypt hashes, plaintext passwords, credentials, or legacy `httpNodeAuth` as Dashboard users.
- Disk identity is the normalized whole-disk PTUUID, never `/dev` name. A duplicate PTUUID on one host is a synchronization error because it usually indicates an unfinished clone.
- Disk names synchronize by explicit UTC modification timestamps, including an empty-name tombstone. Host/device attachment records are separate from the global disk record.
